Follow the existing `ResourcePage`/`ServicePage` shape rather than inventing a third.
- [x] 1.2 Add `IBookingManagementStore` with one list method taking a `BookingQuery` and returning `BookingPage` — **not** `DomainResult`. Management store reads return the page directly; only mutations carry failures. Getting this backwards makes it the only validating store in the codebase.
- [x] 1.3 Enforce the window against `SiteBookingSettings.MaxQueryRangeDays`, failing with `FailureCodes.DateRangeTooLarge` (and `DateRangeInvalid` for a backwards window). **Revised at apply, after the §4.5 sweep:** this began as an `IBookingQueryService`, which `bookings` forbids — *"No Core service SHALL depend on a management store"*. The guard now lives in `BookingQuery.Create`, which is stronger (an invalid query cannot be constructed, not merely rejected) and leaves the sibling `SHALL` intact. Chris chose this over amending `bookings` or moving the service to the Backoffice assembly.
- [x] 1.4 Make the window non-optional in the type, so "list every booking" cannot be expressed. A guard the caller may skip is not a guard.
- [x] 1.5 Register the store, scoped, matching the stores they compose — a singleton over scoped stores captures a disposed scope's DbContext on the second request. **Task text corrected at apply:** there is no Core composer. `UBookItPersistenceComposer` registers the Core services (`AvailabilityService`, `BookingService`, `ServiceBookingService`) as well as the Sql stores, so both registrations go there.

## 2. The SQL implementation

- [x] 2.1 Add `SqlBookingManagementStore` joining `BookingRow` → `ClaimRow` → `ResourceRow` so a summary carries resource **names**. `ClaimRow` holds only `ResourceId`; without the join every row costs a lookup per claim, which is the cost this port exists to remove.
- [x] 2.2 Match the window by **overlap**, half-open `[fromUtc, toUtc)`, the same as `IBookingStore.GetClaimsAsync`. Assert a booking that starts before the window and ends inside it is returned — the case a naive `StartUtc >= from` predicate silently drops.
- [x] 2.3 Order by `StartUtc` then `Id`, both ascending. A total order, or paging repeats and drops rows.
- [x] 2.4 Apply the status and resource filters in the query, not in memory after paging — filtering after `Take` returns short pages and a wrong total. The resource predicate is `any claim matches any named id`; an empty set means no filter, not `match nothing`.
- [x] 2.5 Compute `Total` over the window and filters, not over the page.
- [x] 2.6 Register the store in the persistence composer beside the other Sql stores.

## 3. Guards that would catch the real mistakes

- [x] 3.1 **Paging over a tie.** Fixture several bookings sharing one start time, read across a page boundary, assert nothing repeats or vanishes. A fixture of distinct start times passes against an ordering with no tiebreak at all — this is the ordering landmine already recorded against this project.
- [x] 3.2 **Overlap, not containment.** One booking starting before the window, one ending after it, one wholly inside, one wholly outside. Assert exactly the first three come back.
- [x] 3.3 **The range guard**, at the boundary and one day past it, asserting the failure code and that no results come with it.
- [x] 3.4 **The default status set** returns blocking bookings only, and asking explicitly for `Cancelled` returns them. Vary the fixture so a query returning everything and a query returning the right thing are distinguishable.
- [x] 3.5 **A booking claiming two resources** comes back **once**, with both resources named — and once in `Total` — both with and without a resource filter that matches both. This is the join fanning out, and it is the likeliest defect in the whole change: a one-claim fixture cannot see it, and neither can a filter naming only one of the two.
- [x] 3.6 **`Total` versus page size** — assert with a `take` smaller than the match count, so returning `Items.Count` fails.
- [x] 3.7 **The join returns the right names**, asserted against resources whose names differ from each other and from anything derivable from an id — so a join that pairs a booking with the wrong resource is visible rather than passing on a single-resource fixture.
- [x] 3.8b **QA round 2 (APPROVE with 1 new MINOR, taken).** The SQL guard from 3.8a selected its clause with `LastIndexOf("ORDER BY")`, which is the clause least likely to be the paging one. In the fully projected query EF emits an outer `ORDER BY` to group the resource collection and **re-adds `[Id]` there as the parent identifier whether or not this store asks for the tiebreak** — so a guard reading that clause would pass in both directions. It read correctly only because the seam is un-projected and happens to carry one `ORDER BY`. Now pinned structurally to the clause before `OFFSET`, with an assertion that `OFFSET` exists at all so the guard cannot go quietly vacuous. Re-mutated: still fails without the tiebreak.
- [x] 3.8a **QA round 1 (2 MAJOR).** Both fixed and re-verified. (a) The per-test window isolation was false: `Matches_by_overlap_not_containment`'s out-of-window booking at `to.AddDays(3)` landed inside `WindowOn(4)`, whose unfiltered exact-set assertion then counted it — green only by xUnit's incidental case order. Stride widened to 10 days, plus an `AssertWindowIsUnusedAsync` precondition so a future collision fails naming the window. Verified with QA's own technique: renaming a method to flip the ordering now passes twice. (b) The `ThenBy(Id)` tiebreak had no covering test and QA supplied the formulation I missed — `IQueryable.ToQueryString()` renders the ORDER BY with no database round trip. `The_generated_sql_orders_by_start_then_id` now fails deterministically when the tiebreak is removed, re-confirmed by mutation. Also taken: the self-contradictory boundary message, a seed `DisplayName` no longer derivable from the id, and the missing-service-filter explanation moved into shipped XML docs.
- [x] 3.8 Mutation-checked both, from a clean build, restoring by edit. **Overlap -> containment IS caught** (`Matches_by_overlap_not_containment` fails). **Dropping the id tiebreak was NOT caught at first** — SQL Server's incidental order for these rows is already stable, so no behavioural test can see it. I concluded it was unobservable; QA showed that was wrong, and 3.8a records the fix. Also learned: SQL Server orders `uniqueidentifier` by its **last six bytes**, not .NET's `Guid.CompareTo` order, so an in-memory sorted expectation disagrees with the database even when the store is right.
